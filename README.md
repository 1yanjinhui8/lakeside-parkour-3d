# 湖畔跑酷 3D

类似地铁跑酷的 3D 网页游戏，单机运行，不需要上线。

## 怎么打开

| 方式 | 说明 |
|---|---|
| 双击 `playable.html` | **推荐。完全离线**，单文件 36.5MB，不需要任何网络和依赖 |
| 双击 `start-game.bat` | 备选，会起本地服务器（需要装 Python 或 Node.js），调试时方便 |
| 网址加 `?q=low` | 手机嫌卡就强制低画质（也可以在 ⚙️ 设置面板里点，选择会记住） |

## 🧪 内测版（`playable-beta.html`）

给测试用的独立副本，和正式版**并存**，互不影响。双击就能玩，打开方式和正式版一样。

| 差异 | 正式版 | 内测版 |
|---|---|---|
| 地图切换 | 每 **3000 米**换一张图（固定顺序：轨道→隧道→城市→燕园→医学部） | 每 **500 米**换一张图（同顺序） |
| 人物死亡 | 撞车 / 支撑柱 / 被保安抓住都会死 | **无敌**，所有碰撞判定直接跳过 |
| 标题 | 胡艺凡快跑 3D | 胡艺凡快跑 3D · 内测版 |
| HUD | — | 右上角多一行 `🧪 内测版 · 无敌` |

- **无敌是跳过 `checkCollisions` 整个函数**，所以穿模是必然的（不判定就不会被挡）。跳跃、重力、车顶站立、坡道抬升都不受影响，手感不变。
- **双人对战时自动取消无敌**（`PKVS_PVP()` 每次调用现算）：PvP 要真判死，不然比不出胜负。
- 没有用「每帧把 `S.transGrace` 拉满」的写法：那是转场无敌的计时器，每帧会被 `-dt` 递减，靠外部维持满值一旦遇到更新顺序变化就会漏一帧、出现偶发死亡。
- **每次改了正式版，都要重新生成内测版**，否则内测版会落后：
  ```
  "D:/PythonAPPS/python386/python.exe" tools/make-beta.py
  ```
  脚本会顺带产出 `.perf-beta.html`（模型走 HTTP 的秒开副本，只用于自动化验证）。

**内测版跟着正式版一起更新**：7 座 GLB 地标、终点 360° 环绕、画质降级阶梯全都在里面，
只是段长改成 500 米、人物无敌。所以想快速验收效果，在内测版里跑就行——
500 米一段（约 30 秒），一两分钟就能把四张图轮一遍，不用在正式版里等 3000 米。

> 自检里「撞车会死」那三项在内测版里是**期望反转**成「撞了也不死」，不是跳过：
> 这样自检仍然在验证「无敌确实生效」，内测版同样是 51/51，不会出现假红灯。
>
> 所有模型都已**内联进单文件**：7 座地标（压过贴图后 11.6MB）+ 角色 + 保安 + 两块校园底板。
> `playable.html` 现在 **36.5MB**（2026-11-01 内存优化前是 128MB；2026-11-04 美术升级后
> 先从 42.1MB 压到 28.0MB，随后为了修「双击版模型加载不了」又把川大校门和新葡京
> 内联回来，涨到 36.5MB）。其中 1.8MB 是内联的 three.js（2026-11-02 内联，之前从
> jsdelivr 拉，CDN 一断双击就是白屏）。
>
> **2026-11-04 这次 14MB 是怎么省下来的**：两块校园底板（8.3MB + 4.2MB）原来以裸 base64
> 内联，占 16.7MB；改成 **gzip + base64**（`gz:model/gltf-binary;base64,...`）后只剩 3.8MB，
> 运行时用浏览器原生的 `DecompressionStream('gzip')` 解压成 Blob 再交给 GLTFLoader。
> 几何数据的压缩率约 23%，贴图几乎不涨。工具：`tools/inline-campus.py`。
>
> **浏览器要求**：需要支持 importmap —— Chrome/Edge 89+、Safari 16.4+。
> 更老的浏览器会看到一屏中文提示（不是白屏），告诉对方换浏览器或在系统浏览器里打开。
> 微信 / QQ 内置浏览器可能不支持，需要「⋯ → 在浏览器打开」。
> 体积怎么压下去的见下面「单文件体积 / 内存」一节。

## 🪨 2026-11-06 晚（五）：群山二改 —— 陡崖、分离石柱、可读的松树

上一版被指「一整块莫名其妙的山体」。问题在两处：峰体只有 5 道环、收分像梯形（不陡）；
树是 2 层锥、没有树干（远看就是绿点）。

### 陡峭感

- 环数 5 → **8 道**，中下部 K 值几乎不收（`1.00 → .93`），最后两段才快速收顶；台状峰柱顶径收到 `0.34r`。
- 竖向岩脊 `rib = 1 ± 0.08·sin(...)` + 1/5 扇区做 `0.76` 的内凹深缝并压暗 24% —— 崖壁不再是一块平面。
- 每三层压一条横向岩层暗带；高宽比从 2.2~3.5 提到 **3.5~5.5**（近/中/远三层半径同步收窄）。
- 峰丛结构改成「主峰 + 错开 0.95~1.45r 的副峰 + 1~2 根独立细石柱」，峰与峰之间留山谷；
  石柱把大块体量切开，这是「峰林」和「一整块山」的分界。

### 树木精细度

- 松树重写：细树干（四片）+ **3~4 层伞状锥台树冠**（不是纯锥）+ 收尖；每层中心随机偏移，树冠不对称。
- 层间压深色缝（仅近景）：一层一层压下去的针叶感，不是光滑绿锥。
- 分级 LOD：近景 4 层 7 边、中景 3 层 5 边、远景 2 层 5 边（按 `fog` 判断），三角数可控。
- 三类树分工：崖顶林（沿顶缘成片）、山脚林线（绕山根 `1.18~1.62r`，把山从地面托起来）、
  崖壁斜松（3~5 棵挂在崖壁中上段向外斜伸，黄山迎客松的姿态）。崖壁的绿主要靠它们，
  不再把整个扇区染绿（之前像贴了一张绿纸）。

### 预算

山体仍是 **1 个 drawcall**：108,009 三角 / 324,027 顶点，湖畔总 drawcall **80**。
比上一版（12.8k 三角）翻了 8 倍，但这台的瓶颈是 drawcall 不是三角数；低端机吃紧时把
`RANGES` 的 `n` 各减 3、或 `nTree` 的 `10 + seed % 5` 调到 7 即可，结构不用动。

### 验收

`node tests/game.test.mjs` 38/38；白天全景 / 地平线 / 树冠特写三张 `screenshots/20261106_群山_*.png`；
无控制台异常。

## 🏔 2026-11-06 晚（四）：湖畔群山 —— 灰岩峰柱 + 崖顶松林

把原来的「纯绿六边圆锥 + 白色雪帽」整体换掉。只取国内山川的**结构特征**，不照搬任何具体景点造型：
张家界（近垂直峰柱 / 顶面平台 / 峰顶孤松）、黄山（花岗岩峰脊、峭壁松、前中远三层峰林）、
漓江（喀斯特峰丛沿岸层层退远、山脚植被贴水）。

### 风格锚点

| 项 | 规格 |
|---|---|
| 岩色 | `#3c464d / #58636b / #75818a / #8e9aa1` 四档灰，按层高与朝光面分配 |
| 树色 | `#2b4634 / #3d6340 / #537a49 / #65864f` 四档绿 + 苔绿 `#4e7042` |
| 灰绿关系 | 山脚一圈林带（4/5 扇区）+ 从山脚爬到山腰的竖向植被缝 + 崖顶草台与松，**不是只在峰顶点几棵树** |
| 峰形 | 五道不规则环、7~9 边竖向节理；2/3 台状峰柱、1/3 尖峰，高宽比 2.2~3.5 |
| 纵深 | 近景 `z≈-170 / h 34~62`、中景 `-262 / 62~104`、远景 `-370 / 92~148`，远景 lerp 到冷蓝灰 `#8a9bab` |
| 山口 | 每层每 7 座留 1 个缺口，避免连成一堵墙 |

### 实现与预算

- 所有峰体 / 岩层 / 松树堆进**一个** BufferGeometry，单材质顶点色（`MeshBasicMaterial`），
  明暗烘焙进顶点色 → **1 个 drawcall、12,840 三角形、38,520 顶点**；湖畔总 drawcall 83 → **81**。
- 不依赖 `mergeGeometries`（工具降级时也不会退化成几十个 mesh）；`hillMat` 仍留给隧道场景的远景山影，
  `mtnMat / snowMat` 在湖畔停用。
- 顶点色不受昼夜光照影响：白天 / 夜晚（`t = 0.86`）灰绿保持同一套识别度，不会像 Lambert 那样入夜糊成黑块；
  代价是夜景里山比周围略亮，按「月光下的峰林」处理。
- 云团保留在山腰之间，接住黄山云海那层空气感。

### 迭代记录（评审 → 具体改法）

1. 首版岩壁过曝发白、绿色只有崖顶小树、峰体矮胖连成一堵墙 → 压灰阶、明暗系数 `0.80+0.32` 改 `0.66+0.40`、
   远雾改冷蓝灰、峰体拉瘦高、加山口。
2. 二版山脚像一条整齐绿腰带、中央主峰细得像烟囱 → 第一道环加 ±6% 高度抖动、
   中央主峰由 `r38/h128` 改 `r52/h112`（加宽降高）。

### 验收

`node tests/game.test.mjs` 38/38；语法检查通过；白天 / 地平线 / 夜景三张实机截图在
`screenshots/20261106_群山_*.png`；改前备份 `playable.bak-20261106-群山改动前.html`。

## 🔧 2026-11-06 晚（三）：城门归位 / 真护城河 / 洞间 50m / 湖面去波光

> 本节覆盖上一轮（晚二）第 1 条「水域统一」与第 3 条「隧道长短表」的数值，历史记录保留作对照。
> 这一轮只动湖畔与隧道的画面与排期，玩法数值、障碍密度、碰撞逻辑一律没动。

### 1. 吊门与铁栅栏不再悬空：根因是「大合并基准差 24m」

`buildTiledDecor` 把城堡主体烘焙进大网格，整组基准放到 `z = 24`，并复制成相差 `span = 324` 的 A/B 两份；
吊桥 / 吊闸 / 旗布因为要动、要飘标了 `noMerge`，被留在 `kept` 里、`z` 仍是各自的 `cz`。
于是它们与门楼**恒差 24m**，回绕周期还不同（单份 span vs 两倍 span），越跑越飘 —— 就是截图里
「吊门和栅栏没安在城堡上」。

- 现在把 5 座城堡的吊桥 / 吊闸 / 旗布收进**两个批次同步组**：同样以 `z = 24` 和 `24 - 324` 为基准、
  同样 `tiling = true`（两倍 span 回绕），子对象带城堡完整坐标；两份副本共用相位，动画不跳。
- `tickCastleGates` 改按 `userData.gatePairs`（按城堡分组的 `[吊桥, 吊闸]`）遍历，桥闸联动与旗布飘动保留。
- 运行时实测：滚动 2.5s / 7.0s 两组 z 分别为 `30.9 / -293.1`、`44.9 / -279.1`，**完全一致**；
  把 z 推到 349 触发回绕后两组同时落到 `-298.76`，仍一致。

### 2. 城堡坐在陆地岛上，护城河只是中间一圈水

旧水面内边界 `face + 2.05` 比台基半宽 `face + 3.2` 还小（水淹到墙根），石岸又被整片水面盖住，
观感就是「城堡建在水上」。现在按四层拉开：

| 层 | 范围 | 材质 |
|---|---|---|
| 城堡台基 | `face + 3.2` 以内 | 青灰石 |
| 内岸干地 | 约 2.0m | 灰绿陆地 |
| 护城河 | 约 5.9m | 深蓝水面 |
| 外岸干地 | 约 3.3m | 灰绿陆地 + 两道浅灰砌石护岸 |

- 河的内外各压一道 `0.7K` 宽砌石护岸，边界一眼能看出来；吊桥长 `6.1K`，落下正好跨过河搭到外岸。

### 3. 隧道：洞间固定 50m，洞长随机且互不相同

- `TUNNEL_GAP = 50`，相邻两洞之间的露天段一律 50m（原来的 58/44/70/96/52 长短表作废）。
- `rollTunnelPlan()` 每次开局随机抽 5 段洞长（110–260m，2m 一档），任意两段至少差 24m；
  兜底时等距铺开也保证 5 段互不相同。`TUNNEL_CYCLE`、柱阵排期、出洞里程全由这张表动态推导。
- 实测两次加载：`126/258/152/198/226` 与 `114/146/178/248/208`，`gaps = [50,50,50,50]`，`unique = 5`。

### 4. 湖畔去掉波光，只留流动

- 湖畔湖面与护城河**不再调用** `ART.applyWaterShine`（校园水面仍保留波光与涟漪注入），
  白色高光碎片贴图 `sparkleTex` 整层删除。
- 换成 `flowTex`：透明底 + 柔和深蓝横向水带 + 细水纹，`repeat (2.5, 14)`，经 `texScroll` 以 `D/14`
  缓慢滚动 —— 看得见水在流，没有白色闪点和涟漪圈。
- 运行时实测：湖畔场景 `waterShine` 材质数 = **0**，drawcall 83，无控制台异常。

## 🔧 2026-11-06 晚（二）：水域统一 / 城门归位 / 隧道长短不一

### 1. 护城河与湖畔湖面改用校园水面的着色

原来只有校园的 `water` 材质有波光，护城河是一块死水、湖畔湖面靠一张滚动的白色碎片贴图。

- 把那段注入抽成 `ART.applyWaterShine(mat, opt)`：**同一份代码**（斜向波矢的 glint + 两套错开网格的涟漪环 + 菲涅尔掠射反射）
  现在同时挂在 ①校园水面 ②城堡护城河 ③湖畔湖面。
- `opt` 可调 `ripple`（涟漪强度）/ `glint`（波光强度）/ `scale`（涟漪圈尺寸）：
  校园 `1.0 / 1.0 / 1.0`、湖畔湖面 `0.42 / 1.0 / 0.62`、护城河 `0.26 / 0.85 / 0.5`（水面窄，涟漪压得更小更淡）。
- 湖畔那张滚动碎片贴图（`sparkleTex`）透明度 0.62 → 0.16，只当碎浪，不再和着色器抢戏。

### 2. 吊桥 / 吊闸搬回城堡正中央，做成真正的城门

之前吊桥铰链在台基前沿、吊闸悬在墙外，从轨道看过去像"挂在两座城堡之间的一块木板"。现在：

- 正面**正中央凸出一座门楼**：两侧门墩 + 过梁 + 黑洞门道 + 石拱套（立柱 + 压顶）+ 门前两级台阶。
- 吊桥铰链挪到门楼前沿（`face + 2.78K`），桥面宽 3.3K 正好卡进门洞；举起时贴着门楼站起，落下时跨过护城河落到对岸。
- 吊闸挪进**门道内部**，行程改成"门槛 ↔ 门楣"（`baseY = Y0+4.0K`，`lowY = Y0+2.27K`）。
- **桥闸联动**：一座城堡两扇共用一条相位——桥放到 35% 之后闸才开始抬，桥一收起闸就落下。
  五座城堡相位不同，路上能看到"有的刚开门、有的已经关上了"。

### 3. 隧道每段长度都不一样

等长 200m 一进一出太规律，改成一张**长短表**：

| 段 | 洞长 | 其后露天 |
|---|---|---|
| 1 | 210m | 58m |
| 2 | 92m | 44m |
| 3 | 168m | 70m |
| 4 | **54m** | 96m |
| 5 | 236m | 52m |

- 周期 = **1064m**（五段之和），管段按各自长度建几何（`tunnelShellGeo(len)` 按长度缓存），
  滚到身后整段回退一个周期；洞口亮度的顶点色渐变按"该段内的相对位置"算，长短洞都成立。
- 柱阵排期跟着改：`tunnelAllowsPillar` 用段内相对位置判断（前 30m 与后 52m 不许起阵），
  `tunnelExitAt` 按长短表返回本段出口——跑完最后一根柱子仍然正好接上出洞。
- 实测（D=1 时）：五个管段前缘分别在 `z = 1 / -267 / -403 / -641 / -791`，
  对应 210 / 92 / 168 / 54 / 236 的洞长与 58 / 44 / 70 / 96 的露天段，长短一眼能看出来。

### 4. 洞顶亮度压到原来的 2/3

### 通用的三件事

1. **世界坐标噪声**：贴图只有 8m 一个循环，远处一模糊就是一块纯色。用低频 value-noise
   按世界坐标打碎草地/树冠/墙面，再加一层「朝下的面压暗」的假 AO，球状树冠才有体积。
2. **树冠揉皱**：底板里的树是正二十面体，一眼就是「绿球插在棍子上」。加载时按顶点位置
   哈希沿法线位移（共享位置位移相同，不会裂），剪影才像树。
3. **画面调色**：纯 CSS 暗角（`#grade`），不占 GPU，手机上还会自动减弱。

## ⚔️ 双人对战（联机）

菜单里多了 **⚔️ 双人对战**：点开是一个完整的对战大厅 —— 起昵称 → 建房 / 加入 → 交换信令码 →
备战 → 倒计时同时开跑 → 双人进度条 → 结算 → 再来一局。

**零服务器**：两台浏览器之间走 WebRTC DataChannel P2P，信令靠复制粘贴的「邀请码 / 回执码」
交换（约 600~900 字符，微信能直接发）。同一局域网内不出网，跨网络靠公共 STUN 打洞。

### 三步联机

| 步骤 | 房主 | 客人 |
|---|---|---|
| 1 | 点「创建房间」→ 复制**邀请码** | — |
| 2 | — | 点「加入房间」→ 粘贴邀请码 → 复制**回执码** |
| 3 | 粘贴回执码 → 点「确认连接」 | — |

连上后双方各看到对方头像与延迟，房主点「开始对战」→ 3-2-1 → 同时开跑。左上角「← 返回游戏」随时能退。

> **同机双开**：大厅默认勾着「同机双开自动传码」，两个窗口会自动交换信令码（BroadcastChannel），
> 不用手动复制。但**两个窗口都得在前台可见** —— 浏览器会停掉后台标签页的 `requestAnimationFrame`，
> 后台那一方会卡在倒计时不动（真人对战一人一机，不受影响）。

### 对局规则

| 项目 | 规则 |
|---|---|
| 模式 | **6 种可选**：1000 / 2000 / 3000 米（先到终点），1 / 2 / 3 分钟（时间到比距离） |
| 死亡 | 撞车 / 撞楼 / 被保安抓住 → 立刻判负，对手直接获胜（不用等对手跑完） |

| 开局 | 房主定开跑时刻，客人按 NTP 式时钟差换算到本地钟，误差通常 <10ms |
| 干扰 | **赛道上随机刷 4 种道具**，吃掉即生效、自动飞向对手：🖋 墨水弹 / 🧪 粘液弹 / 🌫 冷凝雾 / 🔀 反向符 |
| 暂停 | 对局中禁用（单方面停表不公平），Esc / P 无效 |

两种都会实时显示对手跑到几米。

### ⏱ 对局模式

房主在备战大厅选，选完同步给客人。两种结束条件、两种判定方式：

| 模式 | 结束条件 | 胜负判定 | 结算文案 |
|---|---|---|---|
| 1000 / 2000 / 3000 米 | 有人跑到终点 | 比**用时**（先到者用时短） | 你比对方先到终点 |
| 1 / 2 / 3 分钟 | 时间到 | 比**距离**（跑得远者胜） | 你比对方跑得更远 |

计时赛的 HUD 计时器会变成倒计时「剩 1:23」；进度条按该时长的估算距离缩放，
看的是「我跟他差多少」，不是精确终点。等待屏显示「⏱ 时间到 / 跑了 1234 m」。

实现上只有一处分支：接入层的 `MODES` 表里每个模式带 `kind`（distance/time）和
`judge`（race/distance）——`kind` 决定 loop 里什么时候收局，`judge` 交给 pkvs 决定怎么比。
大厅的模式 id（`d2000`/`t60`）是给玩家看的，和判定用的 `race`/`distance` 分开传。

### 🎁 干扰道具

**赛道上只有一个外观：带问号的金色骰子。** 看不出里面是什么，跑过去吃掉的那一瞬才抽签，
抽出什么就立刻打向对手。落点、滚动、碰撞判定全部复用主模块的 `pickups` 系统 ——
和护盾 / 磁铁那些道具长得一样、滚得一样，不用另造一套世界。

一局 1000m 约 4 个（间隔 200~275m，第一个落在 190~250m）。优先刷在安全道上，被障碍堵住就换一条。
两端各刷各的 —— 你吃到的和打中你的，不是同一个道具。

盒子里可能开出（权重决定出现概率）：

| 道具 | 效果 | 时长 | 权重 |
|---|---|---|---|
| 🖋 **墨水弹** | 视野被墨糊住：外圈糊死，中心留一块**不规则**可见区，还看得见脚下这段路 | 3.6s | 30 |
| 🧪 **粘液弹** | 对手速度 ×0.40 | 2.6s | 26 |
| 🌫 **冷凝雾** | 雾墙压到眼前（`scene.fog` near→6 / far→40）+ 一层白雾蒙版 | 4.0s | 23 |
| 🔀 **反向符** | 左右操作反转（键盘和触屏一起翻） | 4.0s | 21 |

**盒子里有五分之一是坑**。约 **20%** 开出来的是「自家负面」——同一个效果打在自己身上，时长压到
正面的六成（不能比正面更狠：正面是打对手，他还能反抗；负面是直接扣自己的操作窗口）：

| 开出来 | 效果 | 时长 |
|---|---|---|
| 🖤 **漏墨瓶** | 自己视野被墨糊住 | 2.2s |
| 🐌 **沼泽胶** | 自己速度 ×0.40 | 1.8s |
| 💨 **沙尘袋** | 雾墙压到自己眼前 | 2.4s |
| 🌀 **混乱咒** | 自己左右操作反转 | 1.5s |

开出负面时提示牌换成红色「开出 · 漏墨瓶 / 自己也中招了」，并且**不发 attack 事件**——
对手根本不知道你踩了坑。一局 4 个盒子，平均踩 0.8 个（`EVIL_RATE = 0.20`）。

**为什么做成盲盒**：如果盒子上直接写「墨水」，玩家会按"这个我不想要"绕开它 —— 那就等于让玩家
用躲避来筛道具，赛道上那些盒子会变成障碍而不是奖励。盲盒把「要不要吃」变成一个纯粹的
风险/期待决策：吃到就是赚，赚多少看运气，偶尔还得认栽。

吃到会弹一块牌子：「开出 · 墨水弹」+「已扔向对手」。对面回一条 `hitback`，所以还能看到
「✅ 命中」还是「💢 又打中（效果不叠加）」。

**没有背包、没有冷却、没有抗性**：吃到即生效。玩家控制不了什么时候吃到，挡下来就是白捡；
同种效果重复命中只把结束时间推到更晚的那个，不叠加。

实现上有三条线不能碰：

1. **道具位置用本地随机**，既不按 seed 派生、也绝不进 `spawnRow` 那条 `pkRnd` 流。
   往那条流里多塞一次随机，两端的障碍布局立刻错开 —— 这个坑踩过一次。
2. **两端各刷各的**，位置和类型互不相干。曾经做过「同 seed 两端一致」图个公平，实测是个死结：
   两人在同一位置吃到同一个道具、同时互相扔，效果正好抵消，干扰等于没做 —— 一局实测
   `A@28.5s` 被糊、`B@28.9s` 同时被糊，两边各 3.42s，净效果为零。现在公平性靠
   「一局各 4 个、间隔和权重一致」保证，不再要求是同一个道具。
3. **`CONFIG.powerUps` 混进 `pk_` 之后，主游戏每 500m 的道具点必须过滤掉**。否则单机跑到 500m
   会捡到「墨水弹」然后什么都不发生（单机没有 `__pkPickItem`）。

墨水必须留中心视野窗：全程全黑在跑酷里等价于判死刑，不是「视野受阻」。窗口边缘用极坐标多重
正弦扰动挖出不规则轮廓 + 紫色湿边，才像墨而不是像暗角。

冷凝雾和反向符需要主模块配合，走两个 `[PKVS]` 钩子：`__pkFogAura(scene.fog)` 挂在
`ATMO.update()` **之后**（那里每帧重写雾），`__pkInputFlip()` 乘在 `moveLane` 的入参上
（`campusNoteInput` 必须同步同一方向，否则校园图按原方向判「打没打方向」会误判）。

### 地图一致性怎么保证

三处必须两端完全一致，否则就是"他那边没有这辆车"：

1. **障碍生成**：`spawnRow` 整条链路（含 `placeRide` / `placeBarrier` / `pillarRow`）在生成期把
   `Math.random` 临时换成 `mulberry32(seed)` 的流（`window.__pkRnd`）。逐处替换容易漏，整段换源最稳；
   行距里的速度改用「该行的里程」算，避免速度档位差在两端累计漂移。
2. **换图顺序**：单人已经是固定循环（`SCENE_SEQ`），两端天然一致，不需要再按 seed 排场景表。
3. **迎面车独占判定**：原本看 `obstacles` 里还有没有迎面车 —— 那要看帧时机，两端会差一帧 → 分支不同
   → 后面的随机序列全错开。对局内改成按「里程差 >120m」判定，确定性的。

**开局提前建世界**：倒计时 3 秒里游戏已经在跑，只是速度系数被 `__pkSpeedMul()` 压成 0，到点解冻。
这样那段 200ms 的建图时间不会算进任何一方的成绩。

> 依赖提醒：`three.js` 已经**内联进 `playable.html`**（data URI），纯离线也能跑，两台机器都断网
> 也不影响联机。测试副本 `.perf-*.html` 仍然走本地 `lib/`（避免每次解码 1.8MB base64）。

## 玩法

- **火车**：正面撞上直接结束；灰色坡道可以跑上车顶
- **行驶障碍**：每个地图有一种会**迎面朝你开来**的障碍（见下），任何接触直接失败
- **追捕者**：换道时擦到障碍物会绊一下，保安追到身后；短时间内再绊一次就会被抓住
- **金币**：每枚 10 分，距离每米 1 分；**一局结束后金币入库**，可用来升级道具
- **道具**：🧲 磁铁（自动吸金币）、👟 弹跳鞋（能直接跳上车顶）、✨ 双倍金币、🛡️ 护盾（抵挡一次撞击）、🕊️ **天使之翼（飞行器）**
- **💖 复活币**：稀有道具，**死亡时自动把你救回来**（详见下一节）

## 💖 复活币

**掉落规则**（`REVIVE_CFG`，在 `GAME-DATA` 段，Node 测试共用同一份）：

| 项目 | 规则 |
|---|---|
| 结算频率 | 从 **100 米** 起，每 **100 米** 掷一次 |
| 概率 | 第 n 个 100 米 = **n × 0.5%**（100m 是 0.5%，200m 是 1%，1000m 是 5%…） |
| 保底 | **5000 米必出**（第 50 次不看概率，直接刷） |
| 清零 | 出过一次就归零，下一个 100 米重新从 **0.5%** 开始攒 |
| 持有上限 | 3 个 |
| 出现位置 | 摆在最干净的那条道上，该段不再生成障碍；隧道柱阵区不会摆到被封的中间道 |

**效果**：撞车 / 撞柱 / 被保安抓住时**自动消耗一个，原地复活** —— 清空身前 110 米障碍、2.6 秒无敌、把追上来的保安甩回镜头外，本局继续跑。复活币用完后再死才进结算。

- 外观：金色大币 + 红心徽记 + 双层光环 + 粉色光柱，远处也能一眼认出来
- HUD 左上角金币下面显示持有数（`💖 ×n`），结算面板显示"复活币救场 ×n"
- **换场不会白丢**：刚刷出来还没跑到时正好换地图，会带着它一起搬过去

## 场景与特殊机制

**换场里程**：四张地图统一 **3000 米** 换一次场（`SCENE_SEG_LEN`）。

**固定顺序，不随机**（`SCENE_SEQ`）：

```
湖畔轨道 → 火车隧道 → 城市街区 → 燕园·未名湖 → 医学部 → 回到湖畔轨道 → …
```

每局都从**湖畔轨道**开跑，跑满 3000 米换下一张，五张一轮，循环到底。
没有加权随机、没有"随机轮换"选项，跑到哪一段都能预判下一张图是什么。
**燕园 → 医学部这段走川大门**：燕园段尾声的传送门就是川大校门 GLB
（`assets/models/scu_gate.glb`），穿过去落在医学部环线西南角。医学部跑完回湖畔轨道。

**天气节拍**：晴 / 雨按里程走，**每 5000 米切一次**（`WX_DIST`），跟换场里程互不干扰。
**城市街区少雨少雾**：轮到的「雨」有一半概率直接改判成晴（实测 40% → 18%），
薄雾平均间隔也翻倍（130 秒 → 260 秒）。其它三张图不变，`?wx=rain` 手动指定不受影响。
**薄雾不吃这条节拍**：它按自己的计时进出（90~170 秒一次，每次持续 10~18 秒），
正好赶在 5000 米刻度上也不会被砍断——等雾散了立刻补上那一次待定的切换。

**湖畔轨道 · 北欧式城堡**：左岸一座座北欧式城堡，白 / 黑交替、退距错落。台基 → 壁柱腰线 → 窄高尖拱窗 → 城垛 → 四角圆塔锥顶挂旗 → 顶层退台四坡顶 → 中央主堡，尺度刻意做大，跑起来是压着人走的。

### 城市街区：深夜的分层灯效

夜里**不是**「整条街撒一层窗点」，而是按高度分七层，从下往上逐级收敛：

| 层 | 高度 | 材质 | 夜里目标亮度 | 观感 |
|---|---|---|---|---|

（地面蒸汽踩过同一个坑）。

### 转弯是怎么实现的（不用改相机、不用改玩家）

玩家和其他场景一样**永远在原点、永远朝 -z**，相机一动不动。真正在动的是**整块校园底板**：
每帧按「脚下这段路的切线」把底板绕玩家平移 + 旋转，让当前路段对齐 -z。

- 弯道来临 → 路线切线转了 90° → 底板在 ~14m 内抹过去，画面里整片校园（湖、楼、树）甩过去，
  视觉上等价于神庙逃亡「镜头跟着人转」
- 过弯后新路段又对齐 -z → 前方还是直道，横向道路退到侧面
- 障碍 / 金币 / 道具 / 保安**逻辑完全没动**，仍是一维的 `o.z = 距离`；只是渲染位置改成沿路线投影
  （`placeOnTrack`），所以它们会跟着弯道一起拐

判定规则：

| 项目 | 规则 |
|---|---|
| 需要打方向的路口 | 转角 ≥ **45°**（共 10 个；59° / 66° / 90°） |
| 提示时机 | 距离路口 66m 出箭头（`⬅ 左转 22m` → 按对了变绿色 `已转向`） |
| 有效输入窗口 | 路口前 **72m** 内按下的最后一次左右输入 |
| **底板什么时候转** | **玩家按对之后才转**（限速 0.13 rad/m，90° 约 12m）。路口前 30m 内还没按 → 底板保持进弯朝向，画面里路自己拐走、人直线冲出去，到路口判负 |
| 没按 / 按错 | 判负，死因分三种：`没打方向` / `方向打早了` / `拐错方向`，统一叫「冲出了跑道」 |
| 路口视野 | 每个 ≥45° 路口沿进弯方向清出 **22m × 42m** 的净空（切掉 13 栋楼），最后 30m 不会再正对一堵墙 |
| 路口净空 | 路口前后 **45m 不放障碍**（迎面车按「相遇点」算，不是落点） |
| 复活币 | 拐弯失败后用 → 整块底板倒回**该路口前 100m** 重来（清场 + 重新铺障碍），不是原地复活 |
| 飞行中 / 转场无敌 | 不判负（飞在天上或过场期间不该被判） |
| 不判负开关 | `window.__noTurnFail = true`（截图 / 自动化用） |

### 这次修掉的两个 bug（2026-10-30 晚）

**① 湖畔轨道场景里叠出了整块燕园。** 症状：跑在铁轨上，湖水和草坪互相闪（一会蓝一会绿），
湖面上还立着教学楼。根因不在底板，在可见性——`campusResetRun()` 无条件写了
`CAMPUS.group.visible = true`，而它被 `resetScene()` 在**任何场景**的死亡重开局都调用；
一旦在轨道场景死一次，整块燕园底板就盖到原点上了。

修法：可见性改成每帧跟当前场景对齐（`campusUpdate` 里 `CAMPUS.group.visible = (curTheme === 'campus')`），
`campusResetRun` 里也带上场景判断。验收：`tools/lakeshot.mjs` 会打印 `plateVisible`，轨道场景必须是 `false`。

**② 湖面被草地盖住 / 岸边一圈锯齿。** 症状：湖的边缘出现梳齿状的绿地/缺口。
根因有三层，逐层修：

| 层 | 问题 | 修法 |
|---|---|---|
| 数据 | z14 瓦片的 `landcover=grass` 是栅格化出来的块状多边形，整片压在湖面上（实测压了湖面 95%） | 绿地按水面做差集，退到岸边 1.6m 外 |
| 精度 | 瓦片把未名湖简化成八边形（32k m² 只剩 40 个点） | 改抓 OSM `relation(21716245)` 的原始外环，226 个点 + 湖心岛内环 |
| 共面 | 水面和草地只差 8cm，200m 距离上深度精度只有 ~5cm | 拉开分层：地面 -0.55 / 水面 -0.10 / 绿地 -0.28 / 场地 -0.24 / 路网 -0.16；水面不再接收阴影（低太阳角下大面积平面会刷出阴影 acne 条纹） |

验收脚本：`tools/campus-src/diag-glb-onlake.py` 直接读 GLB，统计「非水面三角形落在水面上」的数量，
现在是 0（之前是 857 个树的三角形长在湖里）。

### 2026-10-31：校园地图返工（一批「反人类」bug）

昨天那版校园交付后跑起来问题一堆，逐条查证后的结论（每条都能用脚本复现）：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 跑起来像 2 倍速，车「自己会动」，拐弯提示来不及 | `scrollWorld` 里 `campusUpdate(step)` 被**注入两次**，底板按 2× 里程推进，而障碍的 `o.z` 只加 1×step → 障碍相对路线的 arc 每帧漂移 | 删掉重复调用。验收：`tools/speedcheck.mjs` 的 `ratio` 必须是 1.000（之前是 2） |
| 2 | 启动慢、drawcall 偏高 | `loadCampusPlates()` 也被注入两次，8MB 底板解析两遍，还多挂了一整份不可见底板 | 只载入一次（同一机位实测 drawcall 约 146 → 125） |
| 3 | 跑着跑着「撞进教学楼」，正前方像死路 | 建筑剔除只判「**顶点**到路线 < 9m」；一栋 100m 长的楼四角都在 9m 外、整面墙却压在路面上（实测 5 处，最近 0.01m） | `build-campus-plate.v2.py` 改用 shapely 多边形求差，把楼从走廊里切掉（`clip_building`） |
| 4 | 每个路口路面被啃出一个 Y 形岔口，人行道压到车道 | `offset_pl` 沿「前后点连线的法线」偏移 off，90° 路口实际只偏 0.707×off | 改成标准斜接 `off/(1+cosθ)`（`offset_pl`） |
| 5 | 路口草地上冒出一块蓝色三角 | 水面材质带 `polygonOffset`，会被拉到路面之上渲染；岸线与走廊重叠就露出来了 | 水面按人行道走廊 6.6m 裁剪，丢弃 <600㎡ 的碎片（`clip_water`） |
| 6 | 川大校门悬空 4.5m | 代码假设模型包围盒中心在 y=0（抬 `0.15×GATE_SCALE`），实际模型底面就在 0 | 载入时用 `Box3` 量真实包围盒（`GATE_FX.baseY/size/center`），底座落地；黑芯按门体比例重算 |
| 7 | 校门飘在草坪/楼顶（不在路上） | `addScenery` 只设 `position.z`，校园里没有走 `placeOnTrack`，弯道上就偏出路面 | scenery 加 `userData.trackScroll` + `tz`，每帧投影；过场判定改用 `portalZ()` |
| 8 | 校车像一堵斜黄墙横跨两车道 | `placeRide` 对所有车型抽 `[12,18,24,30]`，30m 的校车在弯道上会横过来 | 按车型给长：car 4.2 / schoolbus 11 / bus 12 / truck 15 |
| 9 | — | `#turnHint` 的 CSS 块和同名 div 各被注入两遍 | 去重 |

- 4 座新地标合计约 **2.4k 三角面**（国贸 682 / CBD 402 / 杭州 550 / 苏州 638）+ 广场门屋 228，占总量 1.7%；三角面峰值 12.9~14.4 万。
- 沿 324m 循环扫全程（9/42/82/122/162/203/242/283/322m）：drawcall **125~187，峰值 187，全程 ≤200**，无随里程增长；几何体数稳定在 64~81。
- 塔型排布是确定性轮转（`planFamilies`）：每 6 槽必定把 A~F 各排一次，再在轮内洗牌，最后按「相邻不同 + 324m 接缝不同 + 左右不同槽撞款 + 单侧也六型齐全」校验重试。20 万次采样：相邻同款 **0%**、单侧缺型 **0%**、整条街六型齐全 **100%**、左右同槽镜像 **0 处**（旧实现是加权随机 + 事后交换，相邻同款 28%、六型齐全仅 91%）。

> 测量坑（`tools/dcsweep.mjs` 注释里也写了）：推进里程时**不要**用 `obstacles.length = 0` 防撞死——那只是丢掉数组引用，孤儿 mesh 仍留在 scene 里继续渲染，drawcall 和几何体数会随里程单调虚高（实测能虚高到 274）。正确做法是只把 `S.transGrace` 拉满保持无敌。

### 地标换成美术模型（GLB）

上面 7 座地标默认是代码生成的（每座 550~682 面，这是「建模粗糙」的量化原因）。
现在支持用美术做的 `.glb` 直接替换，**不用改任何代码**。

**怎么用**：把模型按名字丢进 `assets/landmarks/`，重启游戏即生效。

```
assets/landmarks/
├── pearl.glb        # 东方明珠（左 s0）
├── guomao.glb       # 国贸三期（左 s3）
├── bamboo.glb       # 春笋（左 s6）
├── gateSuzhou.glb   # 苏州东方之门（左 s9）
├── gateHangzhou.glb # 杭州之门（右 s1）
├── waist.glb        # 小蛮腰（右 s4）
└── cbd.glb          # 国贸 CBD 群（右 s7）
```

**可以分批交付**：没放的自动回退代码生成版本，控制台只打一行
`[landmark] xxx 没有 GLB，回退代码生成`，不会白屏、不会报错。

建模规范见 **`docs/landmark-glb-spec.md`**（原点在底面中心、正面朝 −x、
X 向 ≤16m、单模型 ≤1.6 万面、材质名带 `window`/`neon`/`trim` 关键词）。

接入层 `js/landmarks.js` 干三件事：

| 职责 | 做法 |
|---|---|
| **归一化** | 包围盒底面中心对齐原点 → 等比缩放到 **72m**（要比 32~64m 的普通塔高出一头）→ 超过 16m 宽再按宽度兜一次（会 warn） |
| **材质接光** | 按材质名分类，`window` 走窗格曲线、`neon` 换成 basic 接霓虹曲线、其余按主体/收边分档。单材质（贴图型）模型额外挂**竖向分层着色器**：每 5m 一条灯线，脚部暖琥珀 → 塔身青白，白天透明度为 0 不发光 |
| **夜间灯带** | 注册时扫顶点记下每 2m / 每 15° 的截面轮廓，用来生成基座光池、冠部灯圈、塔顶信标；三样合并成**一个顶点色 mesh**，一座地标只多 1 个 drawcall |
| **放置** | `clone()` 共享几何与材质，按街道左右自动转 180°，街道版和终点地标环版共用同一套原型 |

> 为什么 GLB 要退出「按材质大合并」：它自带贴图和材质，合并会把不同贴图的几何烘到一起
> （画面出错），而且合并后新 mesh 不带 `userData`，调试时会完全看不到这栋楼存在。
> 代价是 7 座地标各 1~3 个 drawcall，实测 dc 从 112 涨到 147，仍在 200 以内。

**夜间怎么亮（2026-11-01 重做）**：这几座 GLB 都是「单材质 + 白天烘焙贴图」，
墙面比窗还亮。早期是「整张贴图当 emissiveMap 再整体提亮」，夜里就是一块发白的板子。
现在的分层：

| 层 | 做法 | 夜里亮度 |
|---|---|---|
| 基座光池 | 广场上一圈加法混合的暖光（按实测轮廓收半径，不铺到马路上） | 0.55 |
| 竖向灯线 | 着色器按顶点高度切层，每 5m 一条细线，色温随高度从琥珀过渡到青白 | 0.18 |
| 冠部灯圈 | 93.5% 高度套一圈冷蓝（宽扁的「门 / 群楼」跳过，避免横穿马路） | 0.06 |
| 塔顶信标 | 交叉双面片红点（不用 Sprite，静态合并会吞掉） | 0.85 |

塔身基色跟着 `ATMO.state().night` 在 **0.52（白天）↔ 0.07（夜里）** 之间插值：
白天保持贴图原样，夜里压暗才有对比，灯线才读得出来。

#### 实际接入结果（7 座已替换）

美术交付的是 **50 万面/座、3 张 4K PNG**，7 座合计 **418.8 MB / 350 万面**。
直接跑会：加载几十秒、显存吃 1 GB 以上、三角面从 14.4 万涨到 **308 万**（21 倍）。

用 `tools/simplify-landmarks.py` 过一遍 Blender（Decimate 8% + 贴图降到 1024 + JPEG q82）：

| 项 | 原始 | 减面后 |
|---|---|---|
| 单座面数 | 50 万 | **4 万**（bamboo 保留 40%，2 万） |
| 单座体积 | 46~71 MB | **4.1~6.0 MB** |
| 7 座合计 | 418.8 MB | **37.7 MB（9%）** |
| 三角面峰值 | 308 万 | **33.7 万** |

|---|---|---|
| pearl 东方明珠 | 54.0 × 10.7 × 12.0 | ✓ 满高 |
| guomao 国贸大厦 | 54.0 × 8.9 × 8.5 | ✓ 满高 |

> 模型是 0.5 高 × 0.8 宽（0.625:1），差 7 倍。要修只能回 Blender 拉高模型。

**「卡在大楼里」的修法（邻位让位）**：CBD（12.7m）和东方之门（16.2m）因为模型是宽扁比例，
归一化后只有这么高。原来紧邻的槽位还是 40~64m 的常规塔，从街上看它们的体块会把地标围住，
看起来像「嵌在里面」（探针 `tools/overlapprobe.mjs` 证实：并没有真正的几何穿插，
只有塔基压边板和它们接触，y 重叠为 0）。

修法是 `LM_NEIGHBOR_LOW`——把紧邻这两座的槽位换成矮楼：

```js
const LM_NEIGHBOR_LOW = { cbd: 0.30, gateSuzhou: 0.38 };
```

`makeTower(side, family, hMul)` 会按倍率压低高度（下限 15m，别压成矮墙），
`neighborHMul(map, s)` 检查左右邻槽。效果：CBD 周围从 40~64m 降到 12~19m，
东方之门周围降到 12~24m，两座地标的天际线露出来了。

> 这个让位是**按槽位自动生效**的，改动 `LM_LEFT` / `LM_RIGHT` 的排布时不用手工维护——
> 只要邻位表里有对应 kind，新位置自动降高。

**材质**：7 座都是单材质（`Material.001`），没有语义命名。接入层自动识别成
`tex-emissive`——把 baseColor 贴图当 `emissiveMap`、`color` 压到 0.55、
`emissiveIntensity` 只留 0.018（夜里最高 0.118）。不这么做的话整栋楼会像发光板。

**性能实测**（减面后，沿 324m 扫 9 个点）：

| 指标 | 代码生成版 | GLB 版 |
|---|---|---|
| drawcall | 125~187 | **235~263** |
| 三角面峰值 | 14.4 万 | **33.7 万** |
| 几何体数 | 64~81 | 117~131 |

drawcall 涨了约 60，因为 GLB 地标整组退出「按材质大合并」——每座地标的广场/台基/GLB
各占一个批次。要压回去得把「广场+台基」和「GLB 塔身」拆成两次 `addScenery`，
让前者仍能合并，预计能降 50~60 个。

> 踩坑记录：装饰走「按材质大合并」时，`canMergeIntoBatch` 过去只检查 `isMesh`，Sprite / Points / Line 会被判为可合并，但烘焙阶段没有几何可烤，随后整个对象被移除——**地面蒸汽就这样被静默吞掉过**。现在合并前显式拒绝这三类对象，蒸汽也改成了交叉双面片（两张互成 90°，代替 Sprite 的始终朝相机）。

| 项 | 值 | 说明 |

| 补光 | 雾 90/620、相机 far **620**、hemi → ≥1.75、sun → ≥0.85 | 环上的地标在 150~250m，按平时的雾 far=100 全部糊掉 |
| 交还 | `getReturnPose` 直接给跟随相机的理想位姿 | 避免过场结束那一帧"啪"一下跳位 |

**两种视角**（⚙️ 设置面板 → 🎬 终点镜头，选择存 `localStorage['huyifan.finishView.v2']`）：

| 模式 | 半径 / 俯角 / fov | 相机实际高度 | 特点 |
|---|---|---|---|
| **人物视角** | 10m / 10° / 80 | 3.2m | 近乎平视，角色占画面 13%，看得到街道尽头的新葡京；**环被街墙挡住** |
| **全景视角**（默认） | 65m / 26° / 86 | **99.7m** | 高过全部街墙（最高 72m），六座地标 + 新葡京 + 环心舞台同框，角色变小 |

> 为什么全景视角要升到 100m：城市是 22m 宽的峡谷，两侧街墙 32~64m、二排背景塔 46~72m。
> 相机只要低于街墙顶，x=±12 那一排楼就会把环上的地标全部挡住——从街上任意高度看，
> |x|>11 的东西一律不可见（墙顶在视线上的投影比塔还高）。**「所有特色建筑都看得到」
> 在峡谷里只有两个解：相机高过街墙，或者把街墙拆了。** 这里选了前者。
>
> 高度和俯角是绑死的（相机看向取景点）：`相机高度 = gaze + 半径 × tan(俯角)`。
> 抬高 gaze 就能在「高」的同时保持「平」——否则 100m 高、看向角色会得到 57° 俯角，
> 画面里只剩地面，塔顶全被上边界切掉。
>
> 试过但不可行的几条路：① 半径 21m 绕到侧面钻进楼里；② 22m 半径 + 68m 高度，
> 俯角 76° 几乎垂直向下，连地平线都没有；③ 过场期间把城市装饰整体隐藏（`userData.tiling`
> 那两个大网格）——街面是空的，只剩一条发光跑道，看着像 bug。

> 两个必须知道的坑：
> 1. **补光/拉雾要用自己的累加器**。`ATMO.update` 每帧都会按当前时段把 `scene.fog` / `hemi` / `sun` 写回去，直接 `damp(hemi.intensity, …)` 永远从原值出发、根本涨不上去。
> 2. **过场要喂 `raw` 而不是 `dt`**。主循环把 `dt` 夹在 1/30 是为了玩法稳定，低帧率下会让过场变成慢放；模块内部自己会把 delta 夹到 `maxDelta`(0.1s)。

**灯光为什么要分层**：代码版第一版是「一整根同亮度的金柱子 + 一张 44×44 的大光晕」，
看着非常基础——没有明暗关系，整座塔糊成一块。

**换成美术模型后（`assets/landmarks/lisboa.glb`）这个问题更严重**：模型是单材质
（`Material.001`）、贴图是白天光照的 PBR baseColor，直接当自发光用就是**一整块发光板**。
而且它的 UV 是包装 atlas，拿不到「从下到上」这条轴，没法用 `emissiveMap` 做竖向渐变。

所以改成 **shader 按世界高度算**（`onBeforeCompile` 注入）：

| 层 | 做法 | 作用 |
|---|---|---|
| **竖向洗墙（shader）** | 顶点着色器传 `vLisboaY = (modelMatrix * vec4(transformed,1.0)).y`；片元里 `wash = mix(1.0, 0.40, smoothstep(0, 0.70, hN))` | 塔脚 1.0 → 70% 高处沉到 0.40。**不依赖 UV**，单材质也有效 |
| **冠部回升（shader）** | `crown = smoothstep(0.70, 0.96, hN) * 0.55`，和 wash 相加 | 冠部重新亮起来，形成「下亮-中暗-上亮」三段，眼睛有落点 |
| **三层辉光** | 大范围 78×78（0.12）→ 主体 42×42（0.16）→ 冠部热点 20×20（0.36） | 一张大光晕等于给整座塔糊层雾；三层叠加才有「光从塔里透出来」的空间感 |
| **地面光池** | 塔脚 62×62 水平贴地 | 暖光从街面打上来，塔脚不再是"插在地上的一根柱子" |
| **尖针灯** | 顶部 `y = 74-1.2` 一颗小球（`lisboaHot`） | 全塔最亮的一点，远处先看到它 |

材质参数：`color × 0.52`（白天也不过曝）、`emissive = 0xffd88a`（淡金，和贴图暖色相乘不偏脏）、
`emissiveIntensity = 0.72`、`fog = false`（路标必须穿雾）。

> 两个踩坑：
> 1. **中段不能压太狠**。wash 低点一开始设 0.30，塔身中段几乎全黑、窗格细节全丢，
>    看着像「三段断开」。抬到 0.40 才是「暗一档」而不是「挖空」。
> 2. **`customProgramCacheKey` 必须给**。改 shader 的材质如果不带自己的 cache key，
>    会和别的标准材质共用 program，注入的代码被复用成错的。

**模型规格**：原始 99.99 万面 / 71.7 MB / 3 张 4K PNG，减面后 **7.99 万面 / 7.1 MB**（`ratio 0.08`）。
原件在 `assets/landmarks/_hd/lisboa.glb`。

> 洗墙光踩坑：塔身上段和莲瓣冠原本共用 `lisboaGoldLt`，加了 `emissiveMap` 之后冠部会吃到渐变**最暗的一段**（0.44），结果冠比塔身还暗——正好反了。冠部必须单独开一个不带贴图的材质（`lisboaCrown`，0.58）。另外渐变要做成**灰度**，彩色渐变会和 emissive 的橙色叠成一片死黄。

## 天使之翼（飞行器）

拿到后进入 **起飞 → 巡航 → 收翼降落 → 落地缓冲** 四段式状态机：

1. **起飞**（0.55s）：翅膀展开、角色升到 7 米巡航高度
2. **巡航**（约 5s）：按住 ↑/空格 可再爬升 1.8 米，按住 ↓ 直接收翼俯冲；飞行中无视地面障碍
3. **收翼降落**（0.8s）：剩余时间低于 1 秒自动下降；如果正上方有火车，会**降落在车顶**而不是穿下去
4. **落地缓冲**（0.22s）：落地有一次下蹲卸力 + 小幅提速，不会硬着陆

## 性能优化（流畅度）

优化前实测：湖畔场景每帧 **775 drawcall**、**849 个 mesh**，跑起来偏卡。优化后各场景：

| 场景 | drawcall（优化后） | 场景内 mesh 数 |
|---|---|---|
| 湖畔轨道 | **110** | 211 |
| 火车隧道 | **30** | 126 |
| 城市街区 | **95~192**（高塔改造后，随视角变化） | 54（合并后） |
| 阳光校园 | **184** | 343 |

渲染 CPU 时间实测 0.11~0.76 ms/帧（四个场景）。校园降得少一些，是因为它的建筑各自克隆了不同 repeat 的贴图（材质必然唯一），这部分要压下去就得牺牲建筑多样性。城市街区在高塔改造时把「每栋楼克隆贴图」改成了「窗格 UV 烘进几何体 + 11 个共享材质」，drawcall 反而从 276 降到 95~192。

做了这些：

| 手段 | 说明 |
|---|---|
| **装饰按材质合并** | `buildTiledDecor` 把整个场景装饰按材质烘焙成少量大网格；同材质几十个小 mesh → 1 个 drawcall |
| **两副本交替滚动** | 装饰原本以 `span` 为周期重复，所以生成两份副本（相差一个 span），滚过 `span` 后整组后移两倍 span，视觉与原实现一致但只需要 2 组 mesh |
| **静态世界合并** | `mergeStaticWorld` 把天际线、湖、山、围墙等不滚动的东西也按材质合并 |
| **装饰不投阴影** | 阴影 pass 是 drawcall 的大头；玩家/保安/车辆/障碍的阴影保留（玩法相关），装饰不再走阴影 |
| **阴影贴图 2048→1024** | 阴影只铺玩家周围 70m，1024 足够，填充率省 4 倍 |
| **相机 far 420→230** | 雾在 190m 就遮满了，收紧远裁剪让视锥剔除更多远景 |
| **HUD 按需更新** | 之前每 100ms 重建道具列表 innerHTML（触发重排）；改成只在数值/道具集合变化时写 DOM，进度条只改宽度 |
| **FOV 变化阈值** | 相机静止时不再每帧重建投影矩阵 |
| **像素比上限 1.5** | 高分屏不再按 2 倍渲染，省掉一半像素填充 |
| **保安动画跳过** | 不在视野里（dist ≥ 12）时不再计算 17 根骨骼的步态 |

> 加载失败会自动降级：`BufferGeometryUtils` 拿不到时退回逐对象合并，再不行就保持原样。

### 手机画质档位（光影减配）

手机 GPU 的填充率和带宽跟台式机差一个量级。原来那套「PCFSoft 1024 + 5 盏点光 + 1.5 倍像素比」全开，在手机上就是**光影太重 → 掉帧 → 一卡一卡**。现在拆成三档：

| 档位 | 像素比 | 分辨率地板 | 实时阴影 | 点光预算 | 雨丝 / 薄雾 | 适用 |
|---|---|---|---|---|---|---|
| **高** | ≤2.0（dpr<1.25 的屏也按 1.25× 超采样） | 无（可降到 0.8× = 原生） | PCFSoft 2048，每帧刷 | 4 | 1500 / 10 | 台式机、独显 |
| **中** | 1.0 | **1.0（锁死）** | **关**，换脚下投影贴片 | 2 | 800 / 5 | 主流手机（手机默认） |
| **低** | 1.0 + 关 MSAA | **1.0（锁死）** | **关**，换脚下投影贴片 | 1 | 500 / 3 | 入门机、老机型 |

自动判定看 UA + 触屏 + 核心数 + 内存（桌面一律给「高」，4K 屏真跑不动会沿降级阶梯自己往下走）。也可以网址加 `?q=low`，或在 **⚙️ 设置面板**里点一下切换（选择会被记住）。

配套的几处手脚：

| 手段 | 说明 |
|---|---|
| **降级阶梯（特性优先）** | 帧时滑动均值 > 20.5ms 就沿阶梯降一级：① 点光源 + 雨丝 → ② 薄雾精灵 → ③ 视距（76→58）→ ④ 实时阴影 → ⑤ 阴影贴图规格。**分辨率放到最后**，而且手机档被 `minPR=1` 锁死，永远不会为了帧率把画面降糊 |
| **分辨率地板 minPR** | 手机档 `minPR = 1`：1 CSS 像素 = 1 渲染像素。原来的自适应能一路降到 0.68×/0.55×（实际像素比 0.85 / 0.55），这才是「画面很糊」的直接来源 |
| **阴影节流** | `shadowMap.autoUpdate = false`，每 N 帧才重算一张阴影贴图（一帧位移约 0.3m，看不出来） |
| **阴影视锥收紧** | 中/低档把阴影相机从 ±20 / ±35 / far100 收到 ±15 / ±25 / 76 与 ±13 / ±20 / 62：同样 768 的贴图铺得更密，同时剔掉更多投影者 |
| **点光源按优先级裁剪** | 霓虹洗墙灯只在赛博街区点亮（其它场景标 `qOff`，不进 shader 的灯光循环）；隧道顶部两盏次优先。超出预算的直接 `visible=false`，three 就不会把它算进 `NUM_POINT_LIGHTS` |
| **低档投影贴片** | 关实时阴影后，玩家脚下贴一张径向渐变片（随跳跃高度缩小变淡），保住「站在地上」的实感，成本 1 个半透明面 |
| **高刷屏限帧** | 实测刷新率 ≥ 88Hz 时按整数分之一限帧（120Hz→60fps、144Hz→72fps），不再白烧电把手机烤到降频 |
| **小摆件不投影** | 半径 < 0.9m 的锥桶/芦苇/反光条不进 shadow pass |
| **薄雾精灵减量** | 低档只留 5 片雾，被裁掉的雾片连位置更新都跳过 |

#### 实测（AMD Radeon 610M 核显，2560×1440 CSS @dpr3，tunnel 场景）

> ⚠ 下表是 **2026-11-05 之前**（阴影 1024 / 点光 3 / 像素比 1.5）测的。之后高档提到
> **阴影 2048 + 点光 4 + 1.25× 超采样**，填充率约涨 1.5~2 倍，下表的高档帧率已不代表现状；
> 中低档与自适应阶梯没动。真跑不动时自适应会沿阶梯降（最后一档 `scale 0.8` 正好退回原生分辨率）。

按各档自己选的分辨率渲染（就是玩家实际看到的样子）：

| 档位 | 渲染缓冲 | 阴影 | 帧率 | p50 帧时 |
|---|---|---|---|---|
| 高 | 3840×2160 | 1024 | **20.8 fps** | 47.5 ms |
| 中 | 3200×1800 | 768 | **31.4 fps** | 31.2 ms |
| 低 | 2560×1440 | 关 | **50.6 fps** | 19.4 ms |

**低档比高档快 2.4 倍，中档快 1.5 倍。**

把三档强行拉到同一个分辨率（3840×2160）再测，隔离掉分辨率这个变量，剩下的就是纯光影开销：47.1ms → 36.0ms，**关阴影 + 少一盏点光省掉约 24% 帧时间**。

自适应分辨率实测（中档 + 4K 级负载）：scale 1.0 → 0.9 → 0.7 → 稳定在 0.68，帧时从 29ms 压到 15~17ms，之后不再抖动（`good` 计数不会到 3，不会来回跳）。


## 动画系统（已重做）

| 状态 | 关键做法 |
|---|---|
| 跑动 | 帧率无关阻尼、躯干反向扭转、胯部摆动、肘部随速度弯曲、头部稳定、头发/衣角惯性 |
| 起跳 | **预备下蹲**（0.09s 蓄力）→ 拉伸离地 → 顶点收腿 → 下落伸腿 |
| 落地 | 落地瞬间**压缩变形**（squash）→ 0.24s 内回弹恢复跑动 |
| 翻滚 | 旋转中心下移到贴地高度、蜷身抱膝、0→2π 平滑转体、结束正好接回跑姿 |
| 飞行 | 滑翔姿态、随横移侧倾、按 ↑↓ 改变俯仰、头发上扬 |
| 菜单 | 角色转身面向镜头挥手展示 |

所有姿态的平滑系数都由 `dt` 计算（`1 - e^(-rate*dt)`），换帧率不会变形。

## 当前角色是怎么来的（真实模型 + 自动绑骨）

`assets/character.glb` = **Tripo3D 从照片生成的模型**，但它在 Tripo 里导出要付费，
所以我们绕了两步把它变成能跑能跳的游戏角色：

| 步骤 | 做了什么 | 工具/文件 |
|---|---|---|
| 1. 拿到模型 | Tripo 预览时模型已经缓存在浏览器里，从 Chrome 缓存里直接提取出 GLB | `D:\DeepSeek\parkour-swap\extract_all.py` |
| 2. 减面 | 原模型 99.8 万顶点 → **3.6 万顶点**（保留颜色/法线/粗糙度 3 张贴图） | `gltf-transform`（npm） |
| 3. 自动绑骨 | 自动识别左右/前后轴、按人体比例生成 **17 根 Mixamo 命名骨骼**、按骨骼线段距离+半径截断算蒙皮权重 | `tools/autorig.py` |
| 4. 接进游戏 | 骨骼名匹配 → 现有程序动画（跑/跳/翻滚/飞行/落地缓冲）直接驱动真实骨骼 | `playable.html` 的 `loadModelCharacter()` |

**想重新绑骨 / 调权重**：

```bash
# 1) 解压+减面（可选）
npx gltf-transform optimize assets/character_unrigged.glb assets/character.glb --simplify-ratio 0.04
# 2) 自动绑骨（输入必须是「有贴图、无骨骼」的静态模型）
node -e "console.log('用 Python 跑：')" 
python tools/autorig.py assets/character_unrigged.glb assets/character.glb
```

> `character_unrigged.glb` 是没绑骨的原版，留着方便重绑；`Michelle.glb` 是演示/兜底模型。

## GLB 真实骨骼模型（换模型用）

游戏支持加载任意带骨骼的 GLB/GLTF 人形角色，**优先级高于代码拼的角色**：

1. 生成模型（任选其一）
   - **Tripo3D**（国内可访问，有免费额度）：上传照片 → 生成 3D → 可选"自动绑定骨骼" → 下载 `.glb`
   - **Meshy / 腾讯混元 3D**：同上，导出 `.glb`
   - **Mixamo**：模型上传 Mixamo 自动绑骨 → 下载"带动画"或"仅模型"的 `.glb`
2. 把文件重命名为 `character.glb`，放进 `assets/` 目录（覆盖同名文件即可）
3. 双击 `start-game.bat` 打开游戏 —— 会自动加载、自动适配

如果模型**没有骨骼**，先跑 `python tools/autorig.py 输入.glb assets/character.glb` 自动绑骨。

内部做了什么（`playable.html` 里的 `loadModelCharacter`）：

- **自动归一化**：按包围盒缩放到 1.85 米、脚底贴地、水平居中、朝向 -Z
- **自动骨骼匹配**：按骨骼名（Mixamo `mixamorig:*` / Tripo / 通用命名）匹配躯干、头、四肢
- **自动放下 T-pose 手臂**：根据骨骼世界方向算基础旋转；已经是 A-pose 的模型会自动跳过（防止二次旋转拧坏网格）
- **按世界轴驱动骨骼**：姿态角度统一解释成"左右轴屈伸 / 竖直轴扭转 / 前后轴张开"，
  所以无论模型骨骼本地轴怎么摆，跑/跳/翻滚的方向都一致
- **不需要模型自带动画**：游戏用程序动画驱动真实骨骼（跑、跳、翻滚、飞行、落地缓冲）
- 模型加载失败会自动回退到代码拼的角色（控制台会提示）

> `assets/Michelle.glb` 是自带的**演示模型**（Mixamo 骨骼女性角色），用来证明管线可用；
> 你的 `character.glb` 会优先生效。想确认用的是哪个模型：控制台会打印 `[角色] GLB 模型已加载: ...`

## 换角色模型最快路径（3 步）

1. 打开 [Tripo3D](https://www.tripo3d.ai)（国内可访问，免费额度）→ 上传你的全身照 → 生成 3D → 勾选"自动绑定骨骼" → 下载 `.glb`
2. 把下载的文件改名成 `character.glb`，覆盖 `assets/character.glb`
3. 双击 `start-game.bat` —— 游戏会自动加载、自动适配骨骼、直接用程序动画驱动

> 加载模型文件需要用 `start-game.bat` 打开（浏览器不允许直接双击的网页读取本地模型文件）。
> 模型加载失败会自动回退到代码拼的角色；控制台（F12）会打印 `[角色] GLB 模型已加载: ...` 方便确认。
